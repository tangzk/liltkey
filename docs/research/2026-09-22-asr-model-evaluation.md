# LiltKey 本机语音模型对比：2026-09-22

本文记录集成前的独立模型评测。随后已按用户选择实现并在本机启用“流式预览 + SenseVoice 定稿校正”，见[实现与验证记录](2026-09-22-streaming-refinement.md)。下文“未改变／未集成”描述的是评测阶段状态。

## 结论

用户明确优先“边说边出字，松键后尽快完成”。本次测试没有找到同时保留现有轻量流式体验、又在中英文上全面改善的单模型直接替代品。

- 中文优先：新版流式 Zipformer-CTC 值得作为可选后端，中文错误率低于当前模型，收尾计算仍很短；它不支持英文，不能作为现有中英双语默认模型的等价替代。
- 中英兼顾：流式 Paraformer 的英文错误显著少于当前 Zipformer，但本次中文指标略差，不能宣称全面升级。
- 准确率优先：Qwen3-ASR 在本次归一化中文与英文指标上最佳；Fun-ASR-Nano 也改善中文，但 CPU FP32 逐句识别约 1.6 秒的中位耗时，不宜直接作为用户当前偏好的默认路径。
- 已安装的 SenseVoice 是低成本定稿候选：本次整句识别中位耗时约 0.18 秒，准确率明显好于当前流式模型。可继续评估保留流式预览、仅在最终提交前用音频重识别的方案；本次只做了独立短句实验，未实现生产集成。

当前运行服务、配置及产品代码未改变；新增模型仅位于独立测试目录。

## 测试条件

- i7-14700K；系统可见约 61 GiB 内存；全程 CPU。
- Python 3.12.14、sherpa-onnx 1.13.7、PyTorch 2.10.0+cpu、Transformers 5.17.0，4 推理线程。
- Google FLEURS test：固定顺序选取时长 3–20 秒且参考文本不重复的前 40 段中文、20 段英文，总长 617.52 秒。未依据模型输出挑选样本。
- 同一批 16 kHz 单声道 PCM16 音频，无语言提示、无热词；模型预热一次后逐句测量，各识别进程顺序运行。
- 当前 ONNX 模型使用已有量化版本；新模型使用官方 native Transformers FP32 路径，没有测试 GGUF、动态量化、torch.compile 或 GPU。

## 60 段文件识别结果

错误率越低越好。中文主评分保留数字格式差异；补充评分对参考与输出同时使用 cn2an 将“十五”等规范成“15”。英文不做数字或英美拼写归一化。两种中文评分均保留，避免把后处理差异误认为听音能力。

| 模型 | 中文原始 CER | 中文数字归一化 CER | 英文 WER | 每段计算耗时中位数 | 进程峰值 RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前 Zipformer 中英双语（2023） | 16.01% | 13.05% | 76.20% | 0.264 s | 0.31 GiB |
| 流式 Paraformer 中英双语 | 16.37% | 13.48% | 35.24% | 0.373 s | 0.42 GiB |
| 流式 Zipformer-CTC 中文（2025） | 13.12% | 10.17% | 不支持（诊断输出 100%） | 0.473 s | 0.30 GiB |
| SenseVoiceSmall INT8 | 8.65% | 8.65% | 6.86% | 0.182 s | 0.44 GiB |
| Fun-ASR-Nano-2512 / Transformers FP32 | 10.31% | 7.64% | 7.78% | 1.557 s | 5.16 GiB |
| Qwen3-ASR-0.6B / Transformers FP32 | 9.16% | 7.07% | 5.03% | 1.587 s | 4.89 GiB |

上述耗时是完整音频的计算耗时，**不是流式模式松键后的等待时间**。流式模型在录音期间已完成大部分计算；整句离线模式则需要在获得整句音频后执行。内存是整个 Python 进程峰值，不是模型文件大小。

## 实时节奏重放

按每 100 ms 到达一块音频，使用现有断句规则，并启用已有 CT-Transformer 补标点。在三段固定短录音上测量“最后一帧音频应到达”到“最终文本处理完成”的时间。混合实验采用 SenseVoice 自带标点，不再重复套用 CT-Transformer；其他三个方案启用 CT-Transformer。包含最后一个音频块和定稿处理，不含麦克风、IPC、输入法及 GUI 延迟；原录音自带的尾部静音也保留，因此不能视作所有松键场景的保证。

| 方案 | 3 段停止后定稿耗时 | 说明 |
| --- | --- | --- |
| 当前 Zipformer 中英双语（2023） | 25 ms / 22 ms / 9 ms | 其中英文短句返回空文本；短耗时不代表正确完成识别。 |
| 流式 Paraformer 中英双语 | 28 ms / 29 ms / 13 ms | 英文能输出，但该句仍有明显识别错误。 |
| 流式 Zipformer-CTC 中文（2025） | 33 ms / 20 ms / 31 ms | 英文不支持，该句结果不作为成功识别。 |
| 现有 Zipformer 预览 + SenseVoice 整句定稿（实验） | 219 ms / 153 ms / 120 ms | 改善“钙、钾”及英文整句；中文短句仍多出一个“传”字。当前流式预览的英文缺陷仍存在。 |

三段依次为 zh-0001（8.28 s）、zh-0011（5.04 s）、en-0004（4.32 s）。首字时间受录音前导静音与发音内容影响，逐条记录在 paced JSON 中，没有将它解释成统一首字延迟。混合实验只覆盖短句、松键时整句重识别，未覆盖连续输入的分段提交、取消竞态或输入法界面行为。

## 观察到的具体差异

- “钙、钾等元素……”：当前 Zipformer 输出“盖甲”，Qwen、Fun、SenseVoice 能正确识别此处。
- 当前 Zipformer 在本次 20 段英文中有多段输出为空；已用系统安装的 `fcitx5-voice transcribe` 在 en-0002 和 en-0004 上复现，不只是实验评分器现象。
- 中文数字格式会显著影响原始 CER；例如“十五”对“15”、中文逐字年份对阿拉伯数字。补充数字归一化是启发式工具，不是官方 FLEURS 评分协议；工具对孤立“万”发出警告并保留原串。
- Fun 的 native Transformers 路径出现官方模型卡亦提及的 attention-dispatch 警告，但 60 段均成功完成；Qwen 与 Fun 均未达到 256 新 token 上限。

## 适用范围与下一步

这些结果仅代表此机器、此运行时和这 60 段公开朗读录音，不代表全部语言、噪声、口音、中英混说或个人口述。模型可能接触过公开测试数据；没有进行训练污染审计。小样本上 Qwen、Fun、SenseVoice 的差距不足以宣称普遍排名。

若继续产品集成，优先验证两条路线：中文模式增加 Zipformer-CTC 可选后端；或保留流式显示、在提交前用 SenseVoice 做轻量定稿。后者需保留每段 PCM、处理取消/分段状态，并在用户实际麦克风录音上验证等待时间和错字改善。此报告不将二次定稿实验宣称为已经上线的功能。

首次新模型文件识别计时与后台下载/解包部分重叠，且桌面没有固定 CPU 亲和性或隔离后台负载，耗时只用于量级比较。流式实时重放在下载完成后执行；没有统计足以支持生产 p95/p99 的样本量。
